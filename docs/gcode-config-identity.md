# Full G-code configuration and generator identity

Mica writes a complete settings footer with PrusaSlicer rules (`prusaslicer_config =
begin/end`) or Orca rules (`CONFIG_BLOCK_START/END`). Binary G-code carries the same
sorted settings in its INI slicer-metadata block, without a duplicate footer in its
executable blocks. This change adds no Cargo dependencies.

## API and CLI

`mica_gcode::full_config::entries(&Config)` supplies sorted upstream key/value pairs;
`text(&Config, used_tools)` supplies the upstream text footer and Orca compatibility
fields. `bgcode_metadata` uses the same serializer. The public `Config::native`
snapshot retains resolved Orca option text separately from template extras and the
canonical settings. It is shared through `Arc`; typed/raw baselines distinguish real
edits from stale aliases and harmless vector expansion during composition.

The printer setting `mica_gcode_identity` accepts `mica` (the general default) and
`orca_compatible`. The CLI spelling is:

```sh
mica slice model.stl --gcode-identity mica -o result.gcode
mica slice model.stl --gcode-identity orca-compatible -o result.gcode
# Also accepted: --set mica_gcode_identity=orca_compatible
```

Snapmaker U1 profile composition supplies `orca_compatible` unless the profile or
project explicitly chooses otherwise. The writer has no U1 identity special case.
The pinned alias version is **2.4.2**, from `orca@8500fcdcca/version.inc`.

With `SOURCE_DATE_EPOCH=0`, the lines are exactly:

```gcode
; generated by Mica Slicer 0.0.1 on 1970-01-01 at 00:00:00
; generated by Mica Slicer 0.0.1 (OrcaSlicer 2.4.2 on 1970-01-01 at 00:00:00)
```

`identity::line_at` accepts an explicit formatted timestamp. Normal exports use
local wall time. Rather than a time library or unsafe FFI, the formatter
uses the platform date utility (`/bin/date`; PowerShell on Windows). The fixed-epoch
path is pure Rust and always UTC, independent of the machine timezone; it also fixes
bgcode's `Produced on`. Invalid/out-of-range epochs fail export. The local formatter
has been exercised on macOS; Windows/Linux runtime formatting still needs review.

## Per-printer file header

Moonraker printers (Klipper and the Snapmaker U1) have a **File header** setting in My
printers: *Automatic (recommended)*, *Mica Slicer* or *Orca-compatible*, stored per printer
in `printers.toml` (`file_header`, and `file_header_detected` for what Automatic learned; the
CLI reads past both). A choice other than Automatic, or what Automatic learned, is applied to
the slice configuration of the printer linked to the current profile as
`mica_gcode_identity`, exactly like `mica slice --gcode-identity` (parity test
`printer_file_header_matches_the_cli_gcode_identity`), so exports to a file and to the printer
use it.

Automatic starts from the profile's default. After each successful upload to a Moonraker
printer the upload thread reads `GET /server/files/metadata?filename=<file>` (read-only,
standard Moonraker, a few short retries while it indexes). When the file carries the `mica`
identity and the printer reports `slicer: Unknown` (older Moonraker forks, including the U1's
firmware, only know a fixed slicer list), the printer switches to `orca_compatible` for future
exports, once, with a notification ("This printer's firmware doesn't recognize Mica Slicer
files; future files use an Orca-compatible header so it shows thumbnails and times"). Metadata
that names a slicer keeps the header. Choosing Automatic again forgets what was learned.

The mock printer covers both Moonraker behaviours (`--moonraker-legacy-slicers`,
`--moonraker-modern`); `printer_filament_tests.rs` uploads through the real dialog path to
each and checks the switch, its single notification and the composed configuration.

## What was ported

- `prusaslicer@b028299c77 src/libslic3r/GCode.cpp`,
  `GCodeGenerator::encode_full_config`, `append_full_config`, and `_do_export`
  (the text call site and `binary_data.slicer_metadata.raw_data`). The existing
  libbgcode port writes those pairs as INI slicer metadata.
- `snapmaker-orca@b1831e5dcb src/libslic3r/GCode.cpp`,
  `append_full_config` / `serialize_gcode_config_option` and the non-BBL footer call
  at 3096–3115. This includes nil-vector omission, filament colours substituted for
  `extruder_colour`, comma-separated flow-support names, the selected tower plate
  coordinate with three decimals **and** the subsequent serialized vector (upstream
  really writes both), then four compatibility fields in upstream order.
- Both upstreams' numeric serializers: six significant digits, C++ stream scientific
  notation thresholds/sign/padding, percent suffixes, and comma-separated scalar points.
  This is isolated from Mica's higher-precision editable settings and move coordinates.
- Both upstreams' string serializers: Prusa scalar strings do not escape quotes;
  Orca scalar strings do. Empty elements in a multi-string vector are unquoted.
- Prusa's profile-level condition/parent fields stay outside its full print config;
  `infill_only_where_needed` is a commented-out definition upstream, although the
  older generated Mica options table still contains it. Mica-only and foreign keys
  are not represented as upstream settings. Prusa filament vectors/IDs are normalized
  to the physical tool count as in `Preset::normalize`.

The Prusa banned set is `compatible_printers`, `compatible_prints`, `print_host`,
`printhost_apikey`, `printhost_cafile`. The Orca set additionally bans
`print_host_webui`, `printhost_user`, `printhost_password`, `printhost_port`.
Foreign host credentials are also refused under Prusa rules; none can be smuggled
through the native snapshot or extras. Native non-secret host-type/authorization
metadata remains when upstream retains it.

There is no BBL export path. Mica exports one plate at a time; profile composition
has already selected Snapmaker flow variants. Native source text wins until its
mapped setting is edited; existing project-dialect translation handles edits.
Unsupported source options are not invented as executable behavior by this footer.

## Reproducibility and gate entry point

```sh
export PATH="/opt/homebrew/opt/rustup/bin:$PATH"
cargo xtask reference-hashes --output /tmp/mica-hashes
# Optional old files: before-cube20-core.gcode, before-3DBenchy-xl.gcode, etc.
cargo xtask reference-hashes --output /tmp/mica-hashes --baseline /tmp/mica-before
```

The tool builds offline, sets `SOURCE_DATE_EPOCH=0`, uses temporary Mica settings,
slices/validates all six manifest profiles/models, checks the regexes, prints raw
SHA-256 hashes, and saves JSON plus full unified diffs. The gate should use this
entry point or set the same environment variable before its existing raw hash check.

`xtask corpus`, `tests/corpus/run.py`, `xtask parity`, and the performance comparison
launcher fix the epoch. Direct GUI/CLI parity tests ignore only the identity line;
with the fixed clock their full same-input outputs are compared byte for byte.
Cross-format Save can legitimately change native percent/vector representations and
persist the GUI's display palette as project colours. Those tests now check unchanged
print commands across Save, then compare the complete footer/output with GUI and CLI
both reopening the same saved project. Program-equivalence tests for different
settings (e.g. filament retraction override versus printer setting) likewise exclude
the deliberately different settings footer. Tests parsing the last layer/statistics
stop before the configuration block.

## Where the code is

- `mica-gcode`: new `full_config.rs`, `identity.rs`, generated option inventory;
  small export/encoder hooks and unified `prusa_metadata.rs` settings.
- `mica-core`: native snapshot/current-value helper and identity option validation;
  no engine/toolpath changes.
- `mica-profiles`: native text capture during mapping and project layering, U1 default,
  upstream filament-self-index bookkeeping; snapshot baselines survive scope changes.
- `mica-cli`: flag and project-colour metadata parity with the GUI when presets change.
- `mica-gui`: fixed-epoch binary timestamp and parity/round-trip test updates.
- `xtask`, corpus/performance scripts, provenance register and third-party data inventory.

The option inventory has a
test against both checked-in schemas so it cannot drift when a pin changes. Tests
cover credentials, deterministic repeats, CLI identity selection, invalid options,
canonical edits retaining untouched native percentages, and text/binary consistency.

## Regex verification

The Python hash tool ran both expressions against every real generated header:

```python
re.search(r'; generated by (.+?) on \d{4}-\d{2}-\d{2} at \d{2}:\d{2}:\d{2}', line)
re.search(r'OrcaSlicer\s(.*)\son', line)
```

Mica mode’s generic name is `Mica Slicer 0.0.1`. Compatibility mode’s generic name is
`Mica Slicer 0.0.1 (OrcaSlicer 2.4.2`; the legacy alias captures version `2.4.2`.
The open parenthesis in the generic capture is inherent in the nested
identity format: the name still identifies Mica and its compatibility alias. The
legacy alias intentionally does not match Mica mode. Both identities retain the
required timestamp shape.
