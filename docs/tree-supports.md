# Tree and organic supports

> **Organic trees (2026-10-18):** `organic` is generated by the faithful PrusaSlicer 2.9.6
> organic port in `support/tree3d/` (Orca's TreeSupport3D tweaks behind `Rules`); see
> [the section below](#organic-trees-tree3d-is-the-generator-2026-10-18). The simplified organic
> path described in the older sections (legacy `organic.rs`) was removed. Classic `tree` style
> (and Orca's `tree_slim`/`tree_strong`/`tree_hybrid`) still uses `tree.rs` as described here.

`support_material_style=tree` and `organic` now select the PrusaSlicer-derived tree pipeline.
Both styles share contact detection, an index-based element arena, bottom-up collision/avoidance
volumes, downward growth and merging of branch influence areas, and upward placement of centres.
Classic tree draws ovalized polygon sections. Organic smooths centres within their influence areas,
extrudes closed branch meshes, and re-slices each branch with `slice::slice_mesh`. Meshes are released
one branch at a time. Both feed the existing shared support schedule, interfaces, raft and lazy
per-layer toolpaths. No dependency was added.

## API and settings

The existing `support::generate(&SupportInput) -> Result<SupportPlan, SupportError>` API is unchanged.
`SupportStyle` adds `Tree`; `Organic` is now implemented. `SupportConfig::tree` is a `TreeConfig`.
`PrintSettings` and config resolution expose all eight existing schema keys:

- `support_tree_angle`, `support_tree_angle_slow` (degrees from vertical);
- `support_tree_branch_diameter`, `support_tree_tip_diameter` (mm);
- `support_tree_branch_diameter_angle` (degrees of downward radius growth);
- `support_tree_branch_diameter_double_wall` (mm; zero disables the second organic wall);
- `support_tree_branch_distance` (mm, spacing when sampling without a continuous roof);
- `support_tree_top_rate` (percentage in configuration, fraction in resolved settings).

The common support settings still control detection, Z/XY gaps, interfaces, first-layer flange,
raft, build-plate-only support, widths and speeds. Trees synchronize their support layers with
object layers, retaining exact non-integral contact Zs. Branch angle limits apply to the outer wall:
radius growth also permits centre movement. Organic branches are hollow, with inward seam anchors;
large islands gain a second wall. Classic tree forces a sheath and retains sparse SupportBase infill.

`SupportPlan::tree_statistics` and `PreparedObject::tree_support_statistics()` report sampled tips,
connected tips, bed roots and model roots. The CLI prints these counts. Graph roots can overlap or
share a flange, so they are not the same as connected deposited footprints. An unconnected tip count
is useful diagnostic information and must not be mistaken for a coverage guarantee.

The pinned `prusa-profiles/PrusaResearch/2.5.12.ini`, the existing full-config fixture, and the installed
reference profile resolve CORE One SPEED to **snug**, support enabled and **automatic detection off**.
The hard-coded `core_one_hf04_speed_pla()` retains that style and adds the profile's tree values
(40°, 25°, 2 mm, 5°, 8 mm, 1 mm, 0.8 mm, 30%). Both complete-config and engine-settings profile tests
were run with the real profile checkout linked. Force automatic detection and the style for oracles.

## Port boundaries and review

All sources are the pinned `prusaslicer@b028299c77`. The tree files retain the Thomas Rahm / CuraEngine
and Prusa Research attribution. `PROVENANCE.md` registers each new adapted Rust file.

- `tree_common.rs`: resolved TreeSupportSettings radius/tip/foot growth, geometric helpers, arena types.
- `tree_volumes.rs`: physical-Z collision slabs, minimum tip clearance, placeable areas, upward
  avoidance propagation and the upstream radius cache schedule. Only requested layer ranges are cached.
- `tree.rs`: overhang tip sampling, small-overhang outward placement, influence expansion/merging,
  upward node selection, landing checks and classic branch sections.
- `organic.rs` (removed 2026-10-18, replaced by `tree3d/`): constrained Jacobi smoothing and
  branch-mesh re-slicing.
- `tree_paths.rs`: hollow organic walls, clipped seams, inward anchors and the double-wall area test.

This is an adaptation, not a line-for-line translation of all 7.7k upstream lines. Important differences:

- Deterministic sequential merging replaces the upstream spatial merge buckets and multi-state
  fast/slow/hole-free search. Merge order and radius freezing change branch count and shape. Mixed bed/model merges retain a
  viable bed route because the separate upstream to-model avoidance state is not implemented.
- Collision caches are single-object. There is no build-volume border or other-object avoidance input.
  Enforcer/blocker masks (volumes and painting) are applied by the shared contact detector, see below.
  Mixed soluble tools and separate support tools remain outside this API.
- Contact detection reuses the existing outline detector. Bridge exclusion works when callers supply
  masks; the current object pipeline still does not supply them. Continuous roofs check for actual printable paths; narrow tips
  use a simpler common slab/interface assignment than upstream's separate missing-roof bookkeeping.
- Organic smoothing uses 2D influence and neighbor constraints, not upstream's 3D sphere collision
  nudger. Final slices are trimmed against the object. Review narrow necks and junctions near sloping
  surfaces carefully. Classic output omits `MutablePolygon::smooth_outward` and its special recovery
  of clipped branch radii; it uses rounded polygon operations instead.
- Organic seam anchors use geometric visibility instead of Clipper per-vertex contour provenance.
  The shared backend's previously documented support-fill and contact-scheduling adaptations remain.

The pinned `tests/fff_print/test_support_material.cpp` contains raft and layer-height cases, but no
active tree-specific test cases. Mica extends those behaviors to both tree styles and adds deterministic
geometry, merging, interfaces, disabled modes, exact gaps, object exclusion, model landings,
build-plate-only shelf routing, double walls, invalid settings and manifold branch-mesh regressions.

## Enforcers only: Orca `*(manual)` and Prusa "for support enforcers only" (2026-10-16)

With `support_material_auto = 0` the shared contact detector returns only enforced overhangs:
painted enforcer facets (projected per layer) and enforcer volumes, never automatic overhangs.
Normal, tree and organic supports all go through it. As in PrusaSlicer's and Orca's
`TreeSupport::generate_overhangs`, tree styles widen an enforced overhang by the tip diameter and
remove the lower layer again, so steep enforced walls still receive tips.

The bug was in the profile mapping: Orca's `support_type` and `support_style` were extras-only,
so an Orca `tree(manual)` project or preset kept Prusa's defaults (`support_material_auto = 1`,
grid) and Mica grew automatic grid support everywhere. They now map (orca `SupportParameters`):
`*(auto)`/`*(manual)` set `support_material_auto`; tree types use organic for `default`,
`organic`, `grid` and `snug`, and Mica's classic tree for Orca's `tree_slim`/`tree_strong`/
`tree_hybrid`; normal types use grid, or snug. Orca's organic tree settings
(`tree_support_branch_angle_organic`, `_angle_slow`, `_branch_diameter_organic`,
`_branch_diameter_angle`, `_branch_distance_organic`, `_tip_diameter`, `_top_rate`) map to the
`support_tree_*` options, and `tree_support_wall_count` 0/1 to a 5 mm / no double-wall threshold.
Project settings (GUI) list both `support_material_auto` and `support_material_style` for a changed
`support_type`; the CLI accepts `--set support_type=tree(manual)` (and `support_style`).

## Organic trees: tree3d is the generator (2026-10-18)

The tree3d port (foundations, pathing, drawing: [tree3d-foundations.md](tree3d-foundations.md),
[tree3d-pathing.md](tree3d-pathing.md), [tree3d-drawing.md](tree3d-drawing.md)) is now the only
organic generator, under both rules. `mica_tree_support_engine` and the legacy organic drawing
(`organic.rs`) were removed; `tree.rs`, `tree_common.rs` and `tree_volumes.rs` remain for the classic
tree style. `tree_paths.rs` (hollow branch walls) is shared output code.

### Porting fixes made during validation

Each was checked against the pinned sources (prusaslicer@b028299c77, orca@8500fcdcca):

1. `increase_single_area`: both pins call `polygons_simplify(increased, 0.025 mm)` and **discard the
   result**; the port simplified the influence area. Removing it made lower trunks thinner (Benchy
   CORE One +9.6 % -> +1.1 %). With `support_tree_branch_diameter_angle=0` the port already matched
   (+0.2 %), which isolated the radius-growth path.
2. `generate_support_toolpaths` merges the same-height top contact and interface layers (and bottom
   contacts per the interface settings) before filling. The port filled overlapping contact and
   interface regions separately, so slopes printed interface twice (Orca cat interface +19 % ->
   +0.4 %, interface islands 978 -> 677 vs 633).
3. `tree_supports_generate_paths` (shared hollow walls): loops run on `closing_ex(polygons, eps,
   eps + w/2)` centrelines, the double-wall area test uses that centreline area, and the second wall
   needs exactly one opened island (Orca: any); Orca doubles every organic wall above 100 mm.
   The old code tested the outer area and always doubled (XL Benchy, 3 mm double wall: +13.9 % ->
   +8.0 %).
4. `generate_support_areas` calls `precalculate()` before tips; this also fixes the ignorable radii
   and therefore the radius buckets. The port evaluated everything lazily without them.
5. Branch slicing in `Positive` mode makes every loop CCW (inverted/folded tube lobes stay solid);
   the port dropped them.
6. Orca: `recover_pending_branch_roofs` ported; interface projections regularized separately for
   top and bottom with their own densities (Orca `generate_interface_layers`).
7. Avoidance step count uses 64-bit arithmetic (overflow near 90 degree angles).

Performance: precalculation (collision, hole-free, placeable, avoidance chains, wall restrictions),
the 100-step Jacobi nudge and per-tree drawing run in parallel (upstream uses TBB for the same
loops); every entry is a pure function of earlier stages, so output is byte-identical to serial.

### Prusa support order (2026-10-18)

`mica-gcode::support_order` ports the entity selection/chaining of PrusaSlicer
`b028299c77` `GCode/ExtrusionOrder.cpp::get_support_extrusions`, using the existing
`ShortestPath.cpp::chain_extrusion_entities` / `chain_extrusion_references` port. Bounded
export preparation orders each object's supports per tool before curve fitting. Base and
interface paths are chained together if their tools coincide; explicit separate tools stay
separate. `translate_support_extruder`'s zero-tool choice prefers the first non-soluble layer
tool under Prusa rules. Orca retains its existing tool selection and support chain.

`LayerToolpaths::support_groups` carries fixed-direction organic anchors, inner/outer wall
collections and first-layer sheath/fill collections through scheduling, adhesion prefixing
and instance shifts. These collections can move as a whole but cannot be split or reversed.
The existing fill `chain_polylines` and shortest-path implementations are reused.

There is one deliberate adaptation to the pinned outer-chain call: Mica uses a
start point at the preceding extrusion endpoint, which is carried across export batches.
Pinned `get_support_extrusions` actually calls `chain_extrusion_references(entities)` with
no `start_near`; its `previous_position` is passed to smoothing. Thus this is not a claim
of byte parity with Prusa's support order. Normal support tours still differ substantially:
for example at Z=1.7 in the grid case, Prusa starts at the outer edge (96.72,112.54), whereas
the endpoint-seeded Mica chain starts near the model (129.54,110.18). A short first arrival
can leave a longer support-to-support tour. The overall travel figures are much closer.

## Normal Prusa support ordering and retraction (2026-10-19)

Normal (`grid` / `snug`) supports under PrusaSlicer rules now use the pinned
`FillBase.cpp::Fill::connect_base_support` connector. The prior `FillSupportBase` wrapper
used `connect_infill`, whose shortest-arch policy generated different endpoints even when
the number of base paths matched. The port shares the existing boundary graph and adds
`mark_boundary_segments_overlapping_infill`, `base_support_extend_infill_lines`,
`emit_loops_in_band`, `evaluate_support_arches` / `evaluate_support_arch_cost`, ranked
vertical/horizontal arches, left-to-right zig-zags, caps, T-joints and remaining long arches.
Pointer references become indices; the cost thresholds are computed per fill rather than

### Geometry kernel and nudge fixes (2026-10-20)

The routing comparison (per-layer support filament, overlays of reference and Mica support
extrusion) showed tips matching but branches merging later or elsewhere a few layers below.
Line-by-line audits of tips, volumes, pathing and drawing against the pins found the port's
control flow faithful; the differences were in the geometry primitives and two small upstream
semantics:

1. `polygons_simplify` (Polygon.cpp `simplify_polygon_impl`): Douglas-Peucker on each ring
   closed by its first point, then `SimplifyPolygons(pftNonZero)`, holes kept clockwise. The port
   used Clipper2's `SimplifyPath`, a different algorithm that can drop vertex 0. It runs in every
   `safe_offset_inc`, every avoidance/collision layer and the final organic simplification
   (`tree3d/geometry.rs::polygons_simplify`).
2. ClipperUtils offsets on Clipper 6.4: `offset(Polygons, delta, jtRound, arc_tolerance)` is a
   per-path `raw_offset` with `ShortestEdgeLength = 0.005·delta`, Clipper 6.4 step rounding, and
   miter limits up to 2 treated as 2 (right angles keep full miters). The port used Clipper2
   offsets (ceil steps, no shortest edge, bevels at limit 1.2)
   (`geometry/clip64.rs::offset_polygons_ex`).
3. Tree booleans run with Clipper 6.4 intersection rounding (`clip64::boolean_ex`).
4. `organic_smooth_branches_avoid_collisions`: `dz` is computed from `uint32_t layer_id -
   int layer_idx`, so layers below a sphere's own layer wrap to a huge `dz` and never collide
   (`nudge.rs::collision_layers`).
5. Organic branch meshes and the nudge work in object coordinates as upstream (floats), then
   move back to the bed.
6. Supports read the uncompensated first layer: PrusaSlicer's `slice_volumes` (and Orca) store
   the slices without elephant foot compensation back into the first layer's `lslices`
   (`print.rs`; all support styles).
