# Provenance

Mica Slicer reuses logic from other open-source slicers on purpose: they carry more than ten years of
print-quality fixes. This file records **where every piece of non-original logic comes from**, so the
project stays honest about its origins, stays license-clean, and can pull in upstream fixes later.

`cargo xtask provenance` enforces these rules. CI runs it on every push and fails the build on any violation.

## Rules

1. **Every source file starts with a header** declaring its license and where its logic comes from:

   ```rust
   // SPDX-License-Identifier: AGPL-3.0-only
   // Provenance: original
   ```

2. **The provenance kind is one of three:**

   | Kind | Meaning | Needs `Source:`/`Changes:` and a register row |
   |---|---|---|
   | `original` | Written from scratch for Mica | No |
   | `ported` | Upstream code translated into Rust (a derivative of that code) | Yes |
   | `adapted` | Upstream algorithm or behavior re-implemented without translating its code | Yes |

   When in doubt between `adapted` and `original`, choose `adapted`. Reading upstream code and then
   writing "your own" version of it still counts as `adapted`.

3. **`ported` and `adapted` files name each upstream source** on its own line, plus what was changed:

   ```rust
   // SPDX-License-Identifier: AGPL-3.0-only
   // Provenance: ported
   // Source: orca@8500fcdcca src/libslic3r/PerimeterGenerator.cpp :: PerimeterGenerator::process_classic
   // Source: prusaslicer@b028299c77 src/libslic3r/ExtrusionProcessor.hpp :: estimate_points_properties
   // Changes: Rust port; streams one layer at a time; dropped Arachne branch (see walls/arachne.rs).
   ```

   - `orca`, `prusaslicer`, … are ids from [`upstream/UPSTREAM.lock`](upstream/UPSTREAM.lock).
   - The commit is at least 10 hex characters and must match the pinned commit for that id.
   - The path is relative to the upstream repository root; `:: symbol` names the function or class.
   - If the upstream checkout is present locally, the checker verifies that the path exists.

4. **`ported` and `adapted` files have a row in the register below.**

5. **Commits that bring in upstream logic carry a trailer** for each source:

   ```
   Ported-From: orca@8500fcdcca src/libslic3r/PerimeterGenerator.cpp
   ```

6. **Moving a pin** (for example to a newer Orca release): update `upstream/UPSTREAM.lock`, re-fetch,
   diff every source file listed in the register between the old and new commit, port the relevant
   fixes, then update the `Source:` lines and the register.

7. **Third-party libraries** (crates, data, fonts) go in [`THIRD_PARTY.md`](THIRD_PARTY.md), not here.

## Per-layer custom G-code (colour change, pause, custom and template G-code)

The model (`crates/mica-core/src/custom_gcode.rs`) is a port of PrusaSlicer's `CustomGCode`
types and helpers plus `ToolOrdering::assign_custom_gcodes` (Orca's midpoint variant as a
dialect switch); the G-code blocks (`crates/mica-gcode/src/custom_gcode.rs`) are ported from
`ProcessLayer::emit_custom_gcode_per_print_z` of both slicers. `print_job.rs` and
`tool_ordering.rs` gained the per-layer extruder switches and the colour-change tool pick of
`ToolOrdering::collect_extruders` / `reorder_extruders`; the time estimate gained
`GCodeProcessor`'s printer stops (`M73 C`/`D`). The 3MF files are read and written by
`crates/mica-core/src/threemf/custom_gcode.rs`, adapted from both slicers' importers and
exporters. The CLI options (`crates/mica-cli/src/custom_gcode.rs`), the validator's `M600`
handling and the GUI (slider "+", markers, menus, colour segments) are original. See
[`docs/custom-gcode.md`](docs/custom-gcode.md).

## M6 GUI, view tools (measure, section view, preview colour schemes)

The measure tool ports PrusaSlicer's `Measure.cpp` into `crates/mica-gui/src/measure/`
(`features.rs`: planes by normal flood fill, their border loops, circles and regular polygons
found on the borders, the feature under the pointer; `math.rs`: distances and angles between
features; `mod.rs`: the feature type) and adapts `GLGizmoMeasure`'s selection rules and
dimensioning in `crates/mica-gui/src/viewport/measure.rs`; non-parallel circle–circle distances
are a numeric minimisation instead of GTE's polynomial roots. The section view
(`viewport/section.rs`) makes the clipping plane of PrusaSlicer's painting / cut gizmos a view
tool; its filled cut faces come from `mica_core::mesh_cut::section_cap` (added to the registered
`mesh_cut.rs`). The preview's extra colour schemes follow PrusaSlicer's `libvgcode` view types:
per-record actual speed (a junction / trapezoid planner adapted from `GCodeProcessor`),
volumetric flow, temperature and the emitted acceleration live in `preview/attrs.rs` and its
`attrs.bin` sidecar, and the legend's feature table and tick scale in `preview/legend.rs`;
colour print is the per-layer custom G-code feature's colour segments (below). The shader clip plane, cap rendering, cards, handles, icons,
screenshot flags and monkey actions are original. All are registered below.

## M6 GUI, Text / SVG emboss tool

The Text tool (T, toolbar) is adapted from PrusaSlicer's `GLGizmoEmboss` / `GLGizmoSVG` and
`Emboss.cpp`, `EmbossShape.hpp`, `NSVGUtils.cpp`, `TextConfiguration.hpp` (Orca 2.4 ships the
same code; its key `T` was checked in Orca's `GLGizmosManager::handle_shortcut`). Engine side,
`crates/mica-core/src/emboss/` turns an outline into a closed prism (`polygons2model` with
`ProjectZ` and the `SAFE_SURFACE_OFFSET` front/back offsets of `EmbossJob.cpp`), optionally
lifted onto the surface under it (Mica refines the flat triangulation and lifts each vertex along
the text Z; upstream cuts the surface with CGAL in `CutSurface.cpp`), builds the placement frame
(`create_transformation_onto_surface`) and maps the editable source to PrusaSlicer's 3MF
`<slic3rpe:text>` / `<slic3rpe:shape>` part elements (Orca writes the same elements into
`model_settings.config`), with the SVG file stored at `filepath3mf`. GUI side,
`crates/mica-gui/src/emboss/` lists fonts (bundled IBM Plex, SIL OFL 1.1, plus the system's,
read in place with `skrifa`), shapes text with `harfrust`, flattens SVG fills parsed by `usvg`
with nanosvg's flatness test, and is the tool card. `emboss/editor_tests.rs`, `emboss/ui_tests.rs`, the scene/save/
viewport hooks and the monkey actions are original. `mesh_cut.rs` gained a `triangulate_2d`
wrapper over its existing ear clipper.

## M6 GUI, model library (Library tab, `crates/mica-library`)

The new `crates/mica-library` crate (index, scanner, file-event watcher, metadata
extraction, search and filters, the synthetic test library) and the GUI side
(`crates/mica-gui/src/library.rs`, `panels/library.rs`, the Library tab in `panels/topbar.rs`,
the Preferences section, the screenshot flags and the monkey actions) are **original** Mica
code. The keys it reads from 3MF projects and G-code (`printer_settings_id`,
`filament_colour`, `extruder_colour`, `; thumbnail begin`, `; estimated printing time
(normal mode)`, Orca's `slice_info.config` `prediction` / `weight`, the bgcode metadata
blocks) are file-format knowledge shared by PrusaSlicer, OrcaSlicer and Mica's own output; no
slicer code was read or translated. Rendered thumbnails reuse the already registered CPU
thumbnail renderer (`crates/mica-gcode/src/thumbnails/render.rs`); binary G-code is read with
the already registered `bgcode::stream::visit`. The QOI and Base64 decoders follow the public
format specifications. New crates are listed in THIRD_PARTY.md.

Background thumbnails, the details preview and drag-to-plate are **original** Mica code as
well: `crates/mica-library/src/render.rs` (the render queue's mesh loading, vertex-clustering
simplification and triangle budget), the worker's render queue,
`crates/mica-gui/src/library_preview.rs` (the orbit preview, the "Fits" chips), `library_drop.rs` (drag payload,
drop targets, parts and the part-kind choice) and their tests. The orbit camera added to the
CPU thumbnail renderer (`render_orbit`) is original; the G-code thumbnail path is unchanged.

## M6 GUI, painting tools

The painting tools (support, seam, colour and fuzzy-skin painting) are original Mica GUI code
(`crates/mica-gui/src/paint.rs`, `panels/paint.rs`, `scene/paint.rs`, `render/paint.wgsl`, the
viewport's brush interaction) over one ported engine file, registered below:
`crates/mica-core/src/painting/selector.rs` is a Rust port of PrusaSlicer's `TriangleSelector`
(the triangle tree that subdivides facets along a brush edge, the circle / sphere / height-range
cursors, smart fill, and the serialisation to the 3MF `TriangleSelector` nibble codes that Mica's
decoder in `painting/mod.rs` already read). Mica keeps a bed-space copy of the vertices instead of
transforming per cursor, does not share midpoints with neighbouring triangles (the renderer draws
leaves; nothing stitches T-joints) and compacts by re-serialising; bucket fill, gap filling and
clipping planes were not ported. See [`docs/gui-painting.md`](docs/gui-painting.md).

## Camera video decoding (`crates/mica-videodec`)

`crates/mica-videodec` decodes the H.264 of RTSP printer cameras with the operating system's
decoder (VideoToolbox, Media Foundation, GStreamer) and is **original** Mica code written from
Apple's, Microsoft's and GStreamer's API documentation and the H.264 Annex B byte-stream
format; no decoder code is ported or bundled. It is the only crate that may use `unsafe` (each
block carries a `SAFETY:` comment); its rows are registered below. The `mica-camera` changes
(the RTSP player on the system decoder, the mock camera's recorded clip) are original too. So
are the WebRTC player (`mica-camera/src/webrtc/`) and the mock camera-streamer
(`mock_webrtc.rs`): they implement camera-streamer's HTTP signalling as a protocol (no slicer
logic, no camera-streamer code); the protocol source and the str0m crypto-provider shape are
credited in THIRD_PARTY.md.

## Licensing

Mica Slicer is licensed **AGPL-3.0-only**. Ported upstream code is AGPL-3.0, so Mica must stay
AGPL-compatible. `-only` rather than `-or-later` is chosen because it is compatible with upstream
files licensed either way, while `-or-later` would not be.

Private use carries no obligations. If Mica is ever distributed or offered over a network, its full
source (including this file) must be made available under the AGPL.

**Vendor profiles are data, and `prusa-profiles` states no license.** The same profiles ship inside
PrusaSlicer's AGPL repository (`prusaslicer/resources/profiles/`, older versions). Until this is
clarified, Mica must not *bundle* profiles from `prusa-profiles` in anything it distributes; reading
them at runtime from the user's own PrusaSlicer installation or from a local checkout is fine.
Packaged builds therefore **download** the Prusa bundle: on first need Mica fetches exactly the
pinned `PrusaResearch/2.5.12.ini` (and its bed models, textures and thumbnails) from Prusa's own
public profile repository, the one PrusaSlicer updates from
(`https://preset-repo-api.prusa3d.com/v1/repos/prusa-fff/`), checks each file's SHA-256 against the
pins in `crates/mica-profiles/src/vendor_profiles.rs` / `vendor_profiles/prusa_assets.tsv` and keeps
it in the user's settings folder (`mica profiles fetch`, or the app's download). The served bundle
differs from the git commit only by 16 `thumbnail` lines; both hashes are accepted and slice
identically. **OrcaSlicer's vendor profiles are AGPL-3.0** like Mica, so a packaged build *ships*
a curated subset of the pinned `orca` copy (`cargo xtask bundle-profiles`, vendor list
`SHIPPED_ORCA_VENDORS`: Snapmaker, Ratrig, Prusa (Orca's own Prusa profiles, used for Orca rules), BBL, Creality, Voron, Elegoo, Anycubic, Qidi, Sovol, plus
`OrcaFilamentLibrary`, with their bed models, textures and pictures, OrcaSlicer's LICENSE.txt and a
NOTICE); see THIRD_PARTY.md.
The Prusa test fixtures are derived from PrusaSlicer's AGPL-3.0 copy instead:
`crates/mica-profiles/tests/fixtures/coreone_hf04_speed_pla.ini` is the CORE One selection resolved
from `prusaslicer/resources/profiles/PrusaResearch.ini` (2.4.14) with three short values updated to
2.5.12 (a firmware version string, `mmu_segmented_region_max_width`, one compatibility clause; its
header lists them and an ignored test in `prusa_bundle.rs` re-derives it). The template tests read
their CORE One templates from that file. The PrusaSlicer exports (`crates/mica-gcode/tests/fixtures/`,
`xl5is_cube20_prusaslicer.gcode`) embed only those same values; the XL templates are identical in
2.4.14. Tests that need the full 2.5.12 bundle read the local checkout at test time.
